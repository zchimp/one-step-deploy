# 演进链路
## 发展历史 
#### chatbot 聊天机器人
 17年刚入行的时候其实就有，优云的chatops，可以通过对话形式从已有的知识库中调取某些信息回复，甚至执行一些预设脚本流程workflow。
相关技术就是NLP自然语言处理。主要是了解意图并回复。
边界： 通常只能在预设的规则，决策树或者知识库范围内回答问题，不能自主操作并执行复杂任务。

#### workflow 
一套预设的工作流程，像流水线一样把复杂任务拆解为固定的步骤，按部就班的执行。 例如OA请假审批，财务报销流程，标准化数据ETL处理。
边界：执行路径固定且可预测。AI可以是workflow上的一个节点，整体流程依然是提前预设好的。

#### Agent智能体 
核心特征是自主规划，目标导向。像全能员工一样，给定一个目标，自己思考，规划步骤，调用工具去执行
边界：区别于chatbot和workflow的地方时自主决策能力。不在依赖固定的代码路径，而是根据当前上下文决定下一步该做什么。
场景：自动排查代码bug的程序员，分析竞品和报告的研究院

#### multi-agent
核心特征是分工协作，群体智能。多智能体系统 像一个部门或者团队，多个不同专业的员工组队协作，有人负责设计，有人负责策划，有人负责执行。共同搞定一个复杂的项目
场景：复杂软件开发项目，跨部门的供应链动态调整。

## 常见面试点
1. 什么是 AI Agent？和普通 Chat 对话有什么区别？
普通Chat对话是基于预设定的知识流程，给与固定的回答的一种程序
Agent基于LLM作为大脑，拥有感知，规划，工具调用，循环迭代，反思，状态记忆的自主执行体

# 基础概念
## 基础核心组件
#### 大脑：LLM大模型（Reasoner 推理核心）
承担思考，决策，意图理解，总结。可以当做一个大脑，只能接受信号，给出反馈。
范式：
```
Thought：我需要先查询运维文档；
Action：RAG_Search (query="kafka broker 断开报错解决方案")
Observation：工具返回文档片段
```

#### Memory记忆系统
解决上下文丢失、持续任务跟踪的问题。主要分为两类
1. 短期记忆（上下文）
对话历史、本轮任务的中间结果，放在prompt窗口内。
Prompt通常包含 任务指令、上下文信息、输出格式、约束条件；
解决LLM无状态的问题，每次请求都是独立处理。需要再同一Prompt多轮对话中，加入上下文短期记忆    
比如第一次询问城市天气，第二次让安排一个旅行计划，那么第二次回答时需要根据前一次回答的天气，尽量少安排户外活动。这个天气就是一个对话历史中的中间结果。

2. 长期记忆（外部向量库 / 数据库）
持久存储：用户偏好、历史任务、知识摘要；需要时检索调入上下文。
短期记忆在Prompt结束之后可以丢弃。谁会记得两年前的清晰对话内容。但是长期记忆需要记录下来，类似于日记。
比如用户说我是一个Java程序员，设计一个程序。三个月之后，又提问如何实现冒泡排序，那么根据记忆，用户是一个Java程序员，需要提供Java版本实现的冒泡排序。
长期记忆是从各轮对话中提炼出来，存放在外部数据库知识库中。

`Memory 不是简单拼接对话，Agent 可以自主决定读取哪些记忆、遗忘无用信息`

#### Planner 规划器（任务拆解）
很多建议的ReAct架构中，没有Planner模块，直接使用Prompt中。
接收一个复杂目标，拆成有序子任务。
两种主流范式：
- 增量规划（ReAct）：走一步看一步，动态调整
比如用户现在要求安排一个2天杭州出游计划（天气/景点/餐饮/交通/预算）。那么ReAct形式设计。走一步，出游需要考虑天气（思考），先查询天气（行动），发现明天下大暴雨（观察）。走第二步查询景点需要排除户外（思考），查询场内景点（行动）。
ReAct的优势在于
1. 决策链路可以追踪： 比如每一步思考，行动，观察都有交互的记录，可以被观察，而不是在LLM中隐藏的，直接输出的。
2. 动态容错： 比如在天气查询过程中，接口访问不通，可以重试或者切换其他的方案（比如输出两种）。
3. 突破知识边界：可以根据实时反馈调整，比如天气并不是在我们知识库中可以得到的历史数据，这都是每天更新的数据。
劣势： 
1. 需要多轮迭代，导致延迟非常高，算力（Token）成本上升。
2. 上下文丢失，每次都需要将任务信息存在上下文记忆里，比如我现在知道明天的天气，那下次提问需要将这些都加入上下文，可能造成窗口瓶颈。
3. 隐式不可观测待办列表，每次只能知道已经知道的
适合：复杂的非标准化（探索）业务场景，不适合实时性要求高的极简任务。


- 先整体规划（Plan-and-Slove）：先生成整体任务清单，再依次执行。
比如设计整体设计方案：[task1: 天气, task2: 找景点, task3: 餐饮, task4: 安排交通, task5: 计算预算]
然后按照task列表逐条执行。
Plan-and-Slove的优势在于：
1. 任务列表显示，可观测，可调式，可干预
2. 长期任务不容易遗忘目标，降低目标偏移
3. 适合复杂多步骤的任务，整体思路清楚
4. 便于分工解耦，适配Multi-Agent架构
劣势：
1. 计划出错，难以自救，依赖re-plan机制，前期依赖LLM的planner能力。
2. 无法响应环境变化
3. 不适合高度开放、信息极度不确定的场景。（探索场景）
4. 增加一层调用，有额外的token和延迟。
适合：固定场景，需求明确，可追溯的场景

企业主流方案：p&s做初始规划， Re-Act风格循环执行 + 异常触发重新规划

#### Tool工具集（行动能力）
大模型本身只能 “思考”，无法触碰外部世界，工具提供执行能力。
常见工具：
RAG 检索、搜索引擎、SQL、API 调用、代码解释器、文件读写。

常见实现方案：
1. MCP：提供个给Agent调用的外部工具系统
2. OpenAI Function Calling： 原生函数调用规范，内嵌在Agent中，自行调用
3. REST/Grpc + OpenAPI Tool Registry： 远程工具调用方案


#### Agent Loop智能循环（标志特征）
`思考（Think）→ 行动（Act）→ 观察（Observe)`
持续迭代，判断是否终止任务；是 Agent 和普通 Chatbot 最本质分界线。

## 增强模块
#### Reflection / Critic（反思 & 校验模块）
自我复盘，事实纠正，抑制幻觉

#### Monitor & Termination 终止判断模块
独立规则/模型判断：任务完成、循环过多、触发退出、防止无限Loop

#### Re-planner 重规划模块
P&S 架构专用，执行异常时重新更新计划

#### Orchestrator（调度器，Multi-Agent独有）
多智能体系统里负责任务分发、Agent 通信（Manager Agent）。


# 架构设计
核心组件：Agent Runtime + Memory 层 + MCP 工具平面 + 纠错 / 反思模块 + 权限 & 审计平面
实现：kagent 作为 Agent 运行时；MCP 作为标准工具总线；可替换为 LangGraph 自研 Runtime
## 整体方案
低代码、基于KAgent
1. Agent 运行时：kagent
2. Memory
- 短期会话：Redis（helm）
- 持久对话 + 向量记忆：PostgreSQL + pgvector
3. MCP平面
- helm-chart-mcp + supergateway（只读、变更两套）
- mcp-server-kubernetes（只读）
4. 纠错模块：基于 kagent systemPrompt + 内置反思循环；可扩展 Webhook 审批
5. LLM 网关：LiteLLM / Ollama
优势：几乎不用写 Python 代码，全部 CRD 声明式管理；原生 K8s 生态。

#### 自研 LangGraph Agent（高度定制）
组件清单
1. Agent Runtime：LangGraph Python 服务（容器部署）
2. Memory
RedisChatMessageHistory（短期会话）
Postgres + pgvector（对话存储 + 向量召回）
3. MCP Client：langgraph-mcp 连接远端 Streamable HTTP MCP 服务
4. 纠错模块：自定义 Graph 节点「反思节点」嵌入执行链路
可选：A2A 协议实现多 Agent 分工（规划 Agent → Helm 执行 Agent）
优势：流程完全可控，可实现复杂分支、多级审批、多智能体协作。

## Memory层
Memory 使用策略（工程规范）
短期上下文：Redis，每次 Agent 推理载入
历史案例召回：向量库相似度检索（top-N 案例注入 System Prompt）
自动摘要：超长对话定期 LLM 摘要，防止上下文溢出
记忆隔离：不同租户 / 集群会话完全隔离

#### 短期记忆
1. langGraph进行内存（POC）
2. Redis保存会话ID->消息列表、工具调用轨迹。 设置TTL过期，超时丢失记忆
kagent 原生支持 Redis 持久会话；LangGraph 可使用RedisChatMessageHistory

#### 长期记忆（会话日志）
postgresql+pgvector（合一部署）
表 1：对话原始消息表（会话 id、角色、消息、时间、执行操作）
表 2：Agent 执行轨迹（调用了哪些 MCP 工具、入参、返回结果、耗时）

#### 长期记忆（向量知识库 / Recall Memory）
简单方案：postgresql+pgvector（合一部署）

大规模：Milvus / Qdrant 独立向量引擎

## MCP 工具平面部署方案
MCP Server 集群 + supergateway
绝大多数开源 MCP 仅支持 stdio，必须通过 supergateway 转为 Streamable HTTP，支持多客户端共享
#### 权限隔离
MCP 集群拆分（按权限最小化，非常关键）
分为两组服务，权限隔离，不要混部署：
只读 MCP 组（安全，开放给普通查询 Agent）
- helm-chart-mcp：lint、template、list、get values、history
- mcp-server-kubernetes：get pods、describe、logs（只读）
变更 MCP 组（管控，仅授权运维 Agent）
- helm-chart-mcp：install / upgrade / rollback / uninstall
- 独立 ServiceAccount，独立网络策略，可增加人工审批钩子

`Agent Runtime(MCP Client) <HTTP Streamable> → supergateway → stdio → helm-chart-mcp`
每个 MCP 服务独立 Deployment，ClusterIP Service；
可选：Ingress + HTTPS + Bearer Token 鉴权。

## 纠错 & 反思模块（Self-Correction 自校正）
语法校验 → 执行结果校验 → 反思复盘
解决LLM 生成错误 helm 命令、参数错误、理解偏差、工具调用失败自动重试
#### 前置静态校验
MCP 侧参数校验：helm 命令参数合法性（chart 名称、版本、namespace 格式）
风险规则引擎：禁止删除生产核心 release、禁止无版本升级
实现方式：
supergateway 前置拦截中间件 或者 在 Agent Runtime 内部增加校验中间件

#### LLM 反思模块（核心 Self-Correction）
嵌入 Agent ReAct 循环：
流程：
1. Agent 调用 MCP 工具 → 获取结果（成功 / 报错）
2. 将【指令 + 工具入参 + 错误日志】送入反思 LLM
3. 反思模块输出：
失败原因
是否需要重试
修正后的工具调用参数
4. 控制最大重试次数（例如最多 3 次，避免死循环）
Prompt 示例方向：
“你是运维反思专家，分析本次 helm 操作失败日志，判断是参数错误、集群问题还是权限问题；如果可以修复，请输出修正后的调用参数；无法修复直接终止并给出排查建议”

#### 事后复盘记忆沉淀
当多次遇到同类报错：
自动把「错误指令 + 错误日志 + 修复方案」存入向量知识库；
后续相似问题自动召回历史解决方案，减少重复犯错。
可选增强：Human-in-the-loop（人工介入）
高危操作（helm uninstall、大规模 upgrade）触发人工审批，属于纠错防护的兜底。
