# 整体组件架构
控制平面：etcd → kube-apiserver → kube-controller-manager、kube-scheduler
工作节点：kubelet、kube-proxy，容器运行时（containerd/docker）
附加组件：

## 控制平面（Control Plane / Master 节点组件）
管接口 管存储 管调度 管生成（控制器）
### kube-apiserver
**角色**： 对外网关
对外提供接口，所有操作的网关，唯一入口，所有客户端访问集群资源均需要通过apiserver提供的REST API。
作为网关，提供认证、鉴权、准入控制等功能。
唯一能读写ETCD的组件，ETCD对外是加密的。
无状态，可以轻松水平扩容实现高可用。

### etcd
**角色**： 唯一数据源。集群分布式键值存储。
强一致性数据库，用来保存所有组件的资源状态
必须高可用奇数节点（3/5）保证选举

### kube-scheduler
**角色**： 调度器
负责资源的调度，pod运行在哪个节点上。
调度方式：
- 筛选（Predicate）：比如污点、资源不足、节点亲和
- 打分（Priority）：选出最优节点
- 绑定：通过 apiserver 将 Pod 绑定到目标 Node

### kube-controller-manager
**角色**： 控制器管理器
运行各类控制器，持续调谐资源状态（期望状态 vs 当前状态），比如statefulset，deployment，daemonset等等controller
核心就是持续循环对比期望状态，不断调谐 reconcile



## 工作节点组件（Node，运行业务负载）
### kubelet
**角色**：每个 Node 上的代理，管理本机 Pod
- apiserver小弟，接受指令
- 调用容器运行时，管理pod状态，创建、启动、停止。
- 管理pod生命周期：存储卷挂载、网络、探针
- 上报node和pod的状态

### kubeproxy
**角色**： 维护service，实现service访问
**工作原理**：在节点配置内核转发规则，实现 Service ClusterIP、NodePort、LoadBalance 流量转发，实现 Pod 服务发现
四种模式：
- iptables： 默认老模式，内核天然支持，链式，集群大了响应慢
- ipvs： 高性能，但是需要内核支持，新版本已经标记为抛弃
- userspace： 最老旧，已经淘汰
- nftables： 最新推荐
```shell
# 查看对应模式
kubectl -n kube-system get configmap kube-proxy -o jsonpath='{.data.config\.conf}' | grep 'mode:'
```

### 容器运行时
**角色**: 基石，资源隔离和限制 依赖内核namespace和cgroup技术
**职责**：拉镜像、创建容器、启停容器

## 附加组件
### CoreDNS
**角色**: dns服务器，负责内部域名解析
pod内通过pod名或者service名称访问其他组件，都需要走coreDNS解析名称

###  Ingress Controller
**角色**： 对外网络网关的控制器
只定义规范，需要具体实现，实现包括nginx-ingress，Traefik等
负责七层网络协议路由转发，将外部http流量转发到service。比如获取客户端真实ip地址，service转发之后获取到的是内部ip，必须配置Local策略，无法跨节点转发。


### Metrics Server
**角色**： 提供一些性能指标信息
采集节点、Pod CPU / 内存指标，供 kubectl top、HPA 使用


# 常见流程
### pod创建流程
1. 提交验证
执行kubectl apply -f xxx.yaml
请求提交到apiserver，检查语法（yaml格式，语病），当前操作是否有权限（搭配用户认证），准入控制（是不是修改删除创建资源，比如被人占用）。
2. 持久化状态
apiserver检查没问题，将数据写入etcd，返回创建成功提示。
3. 控制器接管
controller监听到有新的控制器被创建了，对比当前状态是否符合预期，如果不符合，就发送请求给apiserver，要求创建pod。apiserver将pod数据持久化到etcd。
4. 调度决策
scheduler持续监听着apiserver的watch api。发现有新的或者没有被调度的pod，根据资源情况、亲和性规定等规则，挑选合适的node，绑定之后再通过接口将状态更新到etcd中。
5. 节点执行
kubectl监听到自己被分配了新的pod任务，执行创建操作，拉取镜像，创建运行容器。
6. 状态监控和自愈
kubelet持续监控pod状态，并且上报给apiserver
controller持续监听控制器状态，发现跟预期不想符合，则重复请求补全。

### service自动发现机制
service核心作用就是解决pod ip动态变化的问题，每次pod走完一个生命周期，ip就会变化一次。service维护endpoint对象，用来记录所有pod的ip+端口
1. 标签匹配
通过yaml中的selector字段匹配目标pod，带有匹配标签的pod就会自动纳入service的管理范围。service会维护好pod的endpoint。
2. endpoint动态更新
k8s会自动创建一个service同名的endpoint对象，记录所有匹配的pod的ip+端口，当pod状态变化，endpoint列表就会实时更新，确保流量正确转发。
3. kube-proxy实现流量转发
kube-proxy监听endpoint和service的状态变化，然后在节点上更新对应的网络规则，比如更新iptables表。
```shell
# 查看iptables的nat表，主要就是这个表记录规则
sudo iptables -t nat -L -n -v --line-numbers
# Chain KUBE-SERVICES (2 references)
# target     prot opt source               destination
# KUBE-SVC-ERIFXISQEP7F70F4  tcp  --  0.0.0.0/0            10.96.0.1            /* 
```
